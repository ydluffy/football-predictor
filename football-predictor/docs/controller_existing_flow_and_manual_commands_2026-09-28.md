## 4. 已确认的调度问题

1. **显示与实际规则不同。** 本次读取桌面配置，生产任务 ACTIVE，指定小时的第5分钟触发；本地状态仍称固定30分钟心跳。不能用该状态文字判断实际频率。
2. **接口故障原因可能过期。** 本地最新状态仍有 `pending_reschedule=true`，原因称接口不可用；本对话这次调用 `automation_update(mode=view)` 成功显示任务卡。只能证明此对话可读取，不能证明生产对话可写或已修复动态改期。
3. **任务状态筛选不完整。** 选择器只明确排除 `completed`，不能直接新增 paused/cancelled 字段并期望其自动生效。
4. **人工优先级不明确。** 通用 upsert 对同 key 的变更覆盖字段，并可能把 completed 改回 updated；该函数本身未检查人工覆盖的有效期或所有权。不能仅在聊天里说“改了”就保证下一轮扫描不改变计划。
5. **写入缺少统一事务。** 现有覆盖脚本分别写注册表和状态文件；崩溃可能只写成功一半。注册表保存函数也是直接写文件。
6. **空队列处理缺失。** 选择器直接 min(candidates)，没有空候选分支；所有候选被停止等条件排除时应返回可识别的空计划。
7. **调度状态与执行结果混杂。** 登记、唤醒确认、实际触发及产物验证需要分别表示。

这些是代码与配置层面的观察；没有据此修改生产或重跑现有业务。

## 5. 人工命令协议（拟新增）

适用于信息采集、预测研究、历史统计等通用任务。具体下注建议的自动生成与优化不纳入此实现设计。

| 用户表达例子 | 解析为 | 有效范围 |
|---|---|---|
| 查看今天的采集安排 | inspect | 只读，列出平台与本地状态 |
| 把今天的数据质量审计改到北京时间18:30 | reschedule | 指定日期、指定 task_id，一次性覆盖 |
| 今天先暂停阵容资料采集，明天恢复 | pause | 任务类型与日期范围；不暂停整个总控 |
| 恢复刚才暂停的采集 | resume | 引用最近明确的 command_id；多目标时需消歧 |
| 取消今天的补充统计 | cancel | 终态留档，自动扫描不得复活该实例 |
| 现在补跑昨天失败的赛果核验 | run_once | 新执行尝试，不覆盖原失败证据 |
| 撤销刚才的改期 | revert | 引用原命令；重新计算计划，不覆盖期间新增成果 |
| 以后每天把数据审计改为14点 | change_policy | 明确属于长期规则，与“今天”区分 |

上述是设计示例，不是已经注册的命令。任务描述有歧义时先列出匹配项；日期、目标均明确时不重复索要确认。命令不能任意执行用户提供的 shell 文本，执行器使用经过审查的任务类型白名单。

### 命令处理流程

自然语言 → 解析明确目标、时区、范围 → 读取当前 revision → 校验任务状态及依赖 → 保存 command_id 和变更前后值 → 生成新计划 → 持久化待同步事件 → 计算下一唤醒 → 平台更新并回读 → 输出回执。

建议字段：command_id、task_id、action、requested_at、requested_by、source_reference、expected_revision、scope、effective_from、expires_at、before、after、reason、status。

状态建议：received / validated / committed_local / pending_platform_sync / applied / rejected / reverted。

“本地已改，平台待同步”必须单独显示；只有平台回读匹配才显示“唤醒安排已确认”。这仍不是“已实际触发”，触发后另记录 started_at。

### 优先级与并发

明确的有效人工暂停或取消 → 有效人工单次覆盖 → 自动生成计划 → 默认固定检查点。依赖完整性、真实数据时间和资源限制仍须校验，不能伪造数据满足人工时间要求。

- 自动重排读取覆盖层后生成有效计划，不能先覆盖再补救。
- 改期保留稳定 task_id，不把时间拼入永久标识；时间属于可修改属性。
- 运行中任务暂停默认阻止下一阶段或重试；不承诺立即中断，更不能撤回已发生的副作用。
- 每次领取任务后、产生写入前再次核对 revision 与暂停状态，旧执行者不得覆盖新命令。
- 新计划采用原子替换或事务存储；平台调用通过持久待办队列同步，失败可重试。
- 不把当前混合业务注册表直接挂进新的执行器；迁移前逐类审查任务副作用。

## 6. 调整后的每日通用编排

1. 读取日历、任务注册表、未完成历史任务与有效人工命令。
2. 获取实际赛事数据并版本化，11点刷新假设仍须核验。
3. 按数据来源更新时间、研究快照协议和额度生成采集/研究任务。
4. 合并人工改期、暂停和取消；验证依赖，计算有效计划。
5. 持久化计划及下一唤醒意图，更新平台并回读。
6. 唤醒后重新读状态，领取到期任务，执行并关联输入与产物。
7. 记录成功、无数据、部分覆盖、失败等结果，重算下一任务。
8. 次日核实结果、更新历史记录统计；跨日未确认记录继续等待。
9. 月度输出数据质量、预测质量、运行质量与历史记录评估，保留版本，不自动将研究结论转成下注决策。

人工命令可在任一步进入；发生并发时依据 revision 重新计算。暂停一种采集不应阻断独立的历史复盘。

## 7. 最小实施与验收顺序

第一阶段：只读计划预览，展示“原计划、人工覆盖、有效计划、平台唤醒、已执行记录”，先发现不一致。

第二阶段：在隔离测试注册表实现通用命令与事务状态；不修改现有生产注册表。覆盖改期、单次/长期区分、单任务暂停、整日暂停、取消、恢复、撤销、版本冲突、空队列、跨日和执行中暂停。

第三阶段：用无业务副作用的测试任务验证平台更新、回读、真实到点执行和重启恢复。平台精确时刻语法依实际工具支持验证，不能仅凭写入成功宣布可靠。

第四阶段：只迁移已审查的信息采集、预测研究和历史统计任务；观察多个运行周期，旧任务不重复启用。下注组合与金额优化不属于本设计的实现范围。

验收必须包含：人工改期后自动扫描不改回；暂停或取消后不被选择；命令重试不重复执行；已完成记录不被普通赛程刷新复活；本地写成功但平台失败有明确待同步回执；延期和跨日不丢比赛身份；退出或离线期间的漏跑如实记录。
