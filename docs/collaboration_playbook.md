# 项目协作总手册

本仓库当前采用“双层架构”协作：

- `football-predictor/`：唯一正式 Python 工程，负责数据导入、研究、训练、回测、自动化总控、世界杯与体彩相关策略研究。
- `web/`：Next.js 产品界面与在线 API 层，负责页面、交互、Supabase 读写、在线展示与聊天入口。

这份手册的目标只有一个：让本地 Codex、Trae Work、Coze 云端电脑上的多个智能体，以及你本人，都围绕同一套边界和流程工作，避免重复实现、相互覆盖和错误发布。

## 角色边界

### 你本人

你负责目标、优先级、最终验收和是否合并到 `main`。你不需要亲自写前端、数据库或训练脚本，但要决定“现在先做什么、不做什么”。

### Trae Work

Trae Work 作为主协作助手，负责：

- 读取整个仓库并做全局判断
- 制定文档、规范、开发方案和任务拆分
- 接手前端页面、数据库结构、训练接入、文档建设
- 审查不同智能体输出是否冲突

当任务跨越多个模块，或需要看全局一致性时，优先交给 Trae Work。

### 本地 Codex

本地 Codex 优先承担“正式运行环境附近”的工作：

- 维护本地自动化总控
- 跑需要本地凭据、稳定目录和真实产物文件的任务
- 修改 `football-predictor/` 中的自动化、策略和脚本
- 执行 Git 操作、分支提交、推送和 PR 准备

本地 Codex 当前是自动化总控的主要执行者。正式投注、正式台账、正式调度，暂时只在本地环境运行，不迁移到云端电脑。

### Coze 云端电脑

Coze 云端电脑优先承担“可并行、可试验、可比较”的工作：

- 前端开发与页面联调
- 文档整理、方案对比、跨项目比较
- 数据获取层实验和外部项目能力迁移
- Colab / 云端训练准备
- 非生产性的脚本开发与报表整理

云端电脑当前不承担正式自动化总控，不直接写真实台账，不负责正式投注链路。

### Claude Code / OpenClaw / Hermes

这些智能体主要作为“专项协作者”使用：

- `Claude Code`：大范围重构、架构说明、复杂逻辑梳理、长文档重写
- `OpenClaw`：代码搜索、批量替换、批量整理、辅助生成测试或样板
- `Hermes`：资料整合、规则归纳、方案草拟、对比分析

它们不直接作为仓库的最终决策者，只在明确任务范围内工作，并通过分支或补丁交付。

## 环境分工

### 本地电脑

本地环境是当前的正式控制面，适合：

- 运行 `football-predictor/` 自动化总控
- 访问本地凭据和真实手工台账
- 生成正式研究产物与审计文件
- 执行最终 Git 提交与发布前检查

### GitHub

GitHub 是唯一代码真源。所有代码、测试、数据库迁移、配置模板、文档，都以 GitHub 上的仓库为准。

禁止把以下内容当作真源：

- 聊天记录
- 云端电脑某个目录
- Colab 笔记本运行目录
- 本地临时 ZIP 备份

### Supabase

Supabase 是线上结构化数据真源，主要保存：

- `fixtures`
- `odds`
- `fixture_predictions`
- `backtest_runs`
- `team_name_translations`

Web 层展示的数据，优先从 Supabase 读取。Python 研究链路如果要把结果供前端使用，应写入 Supabase，而不是要求前端直接读取本地 `artifacts/`。

### Colab

Colab 是训练和实验工作台，不是长期生产环境。它适合：

- 跑训练实验
- 做临时回测
- 用 Google Drive 暂存训练数据和模型产物

Colab 不负责保存最终代码真源，也不承担正式调度。

## 代码边界

### `football-predictor/`

这里是唯一正式 Python 工程。所有 Python 命令都从这里进入，或通过仓库根目录的 `scripts/project.ps1` 进入。

适合放入：

- 数据导入与标准化
- 特征工程
- 模型训练与评估
- Research Director
- 体彩与世界杯研究
- 自动化总控、影子策略、审计逻辑

不适合放入：

- 面向用户的前端页面
- 依赖浏览器交互的产品逻辑

### `web/`

这里是产品界面和在线 API 层。

适合放入：

- 页面和组件
- 在线聊天入口
- 在线赛程查询和预测展示
- Supabase 接口封装
- 轻量级线上逻辑

不适合放入：

- 大规模训练任务
- 研究型脚本
- 正式自动化总控

## Git 工作流

所有智能体都遵守以下规则：

1. 不直接往 `main` 推送
2. 每个任务使用独立分支
3. 先跑相关检查，再提交
4. 改动完成后通过 PR 合并

建议的分支命名：

- `feature/<topic>`
- `fix/<topic>`
- `chore/<topic>`
- `docs/<topic>`
- `agent/codex/<topic>`
- `agent/coze/<topic>`

建议的提交边界：

1. 规范、配置、文档
2. 数据导入与测试
3. 模型与评估
4. 策略与 API
5. 前端与展示

不要把“代码改动”和“生成产物刷新”混在同一提交里。

## 协作任务分配建议

### 适合交给 Trae Work

- “先梳理清楚整个项目目前做到哪里了”
- “帮我设计云端协作方案”
- “前端和数据库一起推进”
- “把世界杯研究正式接入主项目”

### 适合交给本地 Codex

- “检查当前 Git 状态并安全提交”
- “继续本地自动化总控相关脚本开发”
- “运行本地测试、验证脚本、生成报告”
- “处理 `football-predictor/` 内单点实现”

### 适合交给 Coze 云端电脑

- “帮我做一个新页面”
- “比较另一个项目的数据获取方案”
- “做一版 Colab 训练 notebook”
- “整理前端接口联调文档”

## 生产与实验隔离

当前必须明确区分两类工作：

- 生产性工作：真实自动化总控、正式台账、正式投注、正式审计
- 实验性工作：新前端、新训练、云端比较、Colab 实验、候选策略

原则：

1. 生产性工作只在本地正式环境执行
2. 实验性工作可以在云端电脑、Colab、独立分支中进行
3. 实验结果先进入文档、测试或影子证据，再决定是否进入正式链路

## 开发顺序建议

当前建议按下面顺序推进：

1. 先补齐协作规范、Git 流程、数据库/环境说明、Colab 说明
2. 再把当前本地仓库安全推到 GitHub 新分支
3. 再让云端电脑 clone 同一仓库
4. 然后推进前端、数据库和训练接入
5. 最后才考虑把更多任务迁到云端环境

## 执行前检查

任何智能体在开始工作前，都应先看：

- 根目录 `README.md`
- 本文件 `docs/collaboration_playbook.md`
- `football-predictor/docs/repository_governance.md`
- 与当前任务直接相关的模块文档

如果任务涉及 Git、数据库、Colab、自动化调度或生产数据，必须先确认边界，再改代码。
