# 数据同步与数据真源规则

这份文档专门用来解决多环境、多智能体协作时最容易混乱的部分：数据和产物到底放哪里、怎么同步、谁说了算。

## 一句话总原则

代码用 Git 同步；业务数据用 Supabase；训练数据用外部存储；生成产物不入 Git。

## 数据分类

把项目里的数据分成 5 类，分别对应不同的同步方式。

### 1. 代码与配置

包含：

- `football-predictor/` 的源码与配置
- `web/` 的源码与配置
- `supabase/migrations/` 数据库迁移
- `docs/` 文档
- `.github/` CI

真源：GitHub

同步：Git 分支 + PR

### 2. 线上业务数据

包含：

- 赛程 `fixtures`
- 赔率 `odds`
- 预测结果 `fixture_predictions`
- 回测摘要 `backtest_runs`
- 翻译映射 `team_name_translations`

真源：Supabase

同步：Web 和 Python 通过 Supabase API 读写

### 3. 训练与研究数据

包含：

- 历史比赛数据 CSV / Parquet
- 训练用特征快照
- 外部数据源下载的原始数据

真源：外部存储（建议 Google Drive 或对象存储）

同步：上传到外部存储，再由训练环境下载使用

注意：训练数据一般不适合存入 Supabase 的业务表，也不适合推到 GitHub。

### 4. 生成产物与审计

包含：

- `football-predictor/artifacts/` 下的模型、评估、报告、审计、台账导出
- 运行日志与临时输出

真源：运行环境本地文件系统（必要时复制到外部存储备份）

同步：不通过 Git

### 5. 机密与凭据

包含：

- `.env`
- API key
- service role key
- 任何账号 token

真源：环境变量系统或本地 `.env` 文件

同步：不通过 Git；不通过普通聊天文本长期保存

## 同步策略

### 代码同步（GitHub）

所有智能体都遵守：

1. 不直接改 `main`
2. 每个任务独立分支
3. 合并走 PR

云端电脑与本地电脑切换时，参考 `docs/cloud_computer_setup.md`。

### 数据同步（Supabase）

Web 与 Python 的分工建议：

- Web：展示与在线交互，读写业务表
- Python：训练、研究、自动化；需要展示的结果写入 Supabase

原则：

1. 如果前端要展示，就写入 Supabase
2. 不让前端读取本地 `artifacts/`
3. 不让 Python 研究链路依赖前端的本地缓存

### 训练数据同步（外部存储）

建议使用：

- Google Drive（适配 Colab）
- 或对象存储（如果后续要上云服务器）

推荐目录：

```text
ball-match-prediction-system/
  data/
  outputs/
```

## 多环境的“数据一致性”约束

### 本地环境

本地环境当前是正式运行环境。主要数据来源：

- 自动化总控产生的正式审计与台账（本地真源）
- 本地持有的密钥（不推送）
- 可选：从 Supabase 拉取业务数据

### 云端电脑

云端电脑以协作和开发为主：

- 不保存唯一版本训练数据
- 不保存唯一版本台账
- 数据主要从 Supabase 读，必要时临时下载

### Colab

Colab 以训练和分析为主：

- 数据来自 Google Drive
- 训练产物保存回 Drive
- 不要把产物推回 GitHub

## “单写入者”规则

为避免冲突，以下资源建议同一时间只有一个写入者：

1. `supabase/migrations/`
2. 自动化总控核心调度逻辑
3. 真实台账与审计输出的“正式目录”
4. 任何会影响真实投注的策略参数

如果多人要改同一块，先约定主写入者，其他人通过 PR 提建议。

## 如何把研究结果给前端用

正确方式（推荐）：

1. Python 训练/推理得到概率与建议
2. Python 写入 Supabase `fixture_predictions`
3. Web 读取并展示

不推荐方式：

- Web 直接读取 Python 的 `artifacts/`
- Web 直接读取某台机器本地 CSV
- 让云端电脑成为唯一产物目录

## 数据获取层的“可迁移资产”

当你在云端电脑比较另一个项目的数据获取层时，优先迁移的是：

- 数据源 adapter 的接口抽象
- 字段映射规则与翻译表
- 缺失率与质量门槛（quality gate）
- 重试、限流、缓存策略

而不是直接搬运“某次跑出来的数据文件”。

## 常见问题

### 我能不能把 `artifacts/` 推到 GitHub，方便云端电脑直接看？

不建议。原因：

- 文件大、变化频繁
- 会污染代码 diff
- 会让 PR 无法审查

更好的做法是：

- 关键报告导出成精简版本（Markdown/HTML）并入库
- 或把产物备份到 Google Drive

### 云端电脑跑出的训练结果怎么给本地用？

推荐流程：

1. 训练产物保存到 Google Drive
2. 本地再下载到本地 `artifacts/` 或指定模型目录
3. 手工或脚本注册为“候选模型”，再决定是否晋级

### Supabase 数据和本地数据不一致怎么办？

先明确“这条数据属于哪一类”：

- 如果是线上业务数据：以 Supabase 为准
- 如果是研究训练数据：以外部存储/训练快照为准
- 如果是正式台账与审计：以本地正式环境为准

然后再决定是否需要同步或修复写入链路。
